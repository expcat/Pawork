| spawn 登记与 finish 收子存在窗口，早期取消可能错误记为失败 | admission 与 finish 共锁，发布 spawned 前登记取消令牌；取消封口区分 cancelled，未启动的 Run 补齐 Started 后再记终态；取消与持久化回归通过 |
| 子代理列表失败无局部错误，GUI 无停止动作 | 成功 / 失败均按会话 + 唯一请求号校验，保留旧列表和错误，刷新在加载中禁用，终态事件仍可发起更新请求；面板自动选中运行优先的首项，提供 Stop、pending 与失败重试；AX / 布局回归通过 |

### 真实 CLI 复查发现的能力归属问题

使用当次 `opencode-go / glm-5.3-flash` 与隔离实例 `feature-boundary` 提交已有样例图片时，旧 RunService 只按模型名读取能力，错误接受了 `glm-coding` 同名模型的静态图像声明，与 GUI 目录中未声明图像的状态不一致。模型返回了文字与工具调用，但样例仅为极小占位图，且能力来源错误，因此不计作图像识别验收成功；记录在 `/tmp/pawork-feature-audit/remaining-image-live.log`。

现 RunService 在统一 capability gate 前核对证据的 provider 必须等于实际请求 provider，否则按缺证据拒绝图片 / 托管工具；不按供应商名写特例。扩展原 `capability_gate_rejects_undeclared_web_search_and_image` 用例覆盖同名异供应商图像声明，`services::run::tests` 9 passed；最终再次 `RUST_TEST_THREADS=1 bash scripts/test.sh app`：273 passed、0 failed（`remaining-capability-tests.log`、`remaining-app-final-tests.log`）。

真实托管搜索的剩余条件也已明确：当前 Go API-key 通道的 Chat Completions hosted wire 未接入，Responses 搜索透传亦未声明；指定验证模型不能完成这项正向验收。2026-09-21 核对 [Go 公开目录](https://opencode.ai/zen/go/v1/models)，返回模型 ID 等基本字段，没有图像或搜索能力字段。不能据此编造支持或借用其它通道声明；成功路径仍以本轮自动测试为证据，真实供应商正向验收待具备已声明能力的通道和模型后执行。
